# Delivery

## When / Not When

범위가 정해진 기능·버그·테스트·문서·설정 변경을 수행할 때 선택합니다. 검토·조사만 요청된 경우 해당 Workflow를 우선하며, 하네스 자체 개선이 주목적이면 [Harness Improvement](../harness-improvement/WORKFLOW.md)를 선택합니다.

## Inputs

목표·수용 조건·제외 범위, 현재 기준 ref·관련 계약, 실제 쓰기 권한, 승인 상태.

## Execute

**RPI(R):** 먼저 현재 코드·계약·테스트를 조사(Research)하고 범위·수용 조건을 계획(Plan)합니다. 실제 동작 변경의 Implementation은 아래 **순서대로** 진행한 뒤 Review합니다. 별도 계획 문서는 복잡도가 정당화할 때만 만들며, 짧은 작업도 선후 관계는 유지합니다.

1. **Spec:** 사용자 의도를 관찰 가능한 동작·입출력·오류/경계 사례·비목표·수용 조건으로 명세합니다. 기존 계약과 충돌하거나 중요한 제품·보안 결정이 필요하면 먼저 해결/승인을 구합니다. Spec은 기존 Issue·PR·작업 문서에 짧게 기록해도 됩니다.
2. **테스트 설계:** Spec의 수용 조건별로 검증할 사례, 기대 결과(oracle), 적절한 단위/통합/계약 경계와 회귀 위험을 정합니다. 기대값은 **Spec과 독립적인 계약**에서 도출하며 현재 구현을 정답으로 가정하지 않습니다. 필요한 경우 `mols-test-design`을 활용합니다.
3. **테스트 구현:** 위 설계에 따라 테스트를 **제품 코드 변경 전에** 작성합니다. 실행할 수 있으면 대상 테스트가 의도한 이유로 실패하는지(Red) 확인하고 실패 원인을 구분합니다. 기존 동작으로 이미 통과하는 사례나 실행 불가 환경에서 억지 실패를 만들지 않으며 그 근거·미실행 상태를 기록합니다.
4. **실제 구현:** 명세를 만족하는 가장 작은 코드를 작성해 새 테스트와 관련 회귀 테스트를 통과시킵니다(Green). 그다음 필요한 리팩터링을 수행하고 다시 검증합니다. 테스트를 통과시키기 위해 근거 없이 명세·기대값을 바꾸지 않습니다.
5. **Review:** Spec ↔ 테스트 설계 ↔ 테스트 코드 ↔ 제품 코드의 추적 가능성, 누락된 오류 경로·회귀·보안·검증 비용을 검토합니다. 중요한 결함은 **가장 이른 잘못된 단계**부터 교정하고 재검증합니다. 실패 원인 분석은 [Failure Recovery](../failure-recovery/WORKFLOW.md)를 활용합니다.
6. **인계:** [Routine Loop](../../../docs/development/workflows/routine-loop.md)에 따라 적절한 [mise 검사](../../../docs/development/README.md#checks)와 실제 결과를 기록하고 diff 자체 리뷰·PR 인계를 수행합니다.

**적용 경계:** 문서·포맷·설정 등 **실행 가능한 동작 변화가 없는 작업**에는 의미 없는 테스트를 만들지 않고 Markdown lint 등 직접적인 검증을 사용합니다. 기존 테스트 환경이 없는 경우에도 Spec·테스트 사례/관찰값을 먼저 정의하고, 테스트 자동화의 부재와 실제 수행 가능 여부를 명시합니다. 테스트 구현/Red를 수행하지 못했다면 그 단계를 완료했다고 주장하지 않습니다. 버그 수정도 재현 테스트를 수정 코드보다 우선합니다(가능한 환경에서 Red → Green).

## Exit / Handoff

실제 변경 ref/PR, 수용 조건별 증거, 미확인 위험, 필요한 승인을 전달합니다. **PR 생성은 병합이 아닙니다.** 현재 작업이 단순하면 새 계획서·체크포인트를 의례적으로 만들지 않습니다.
