# Principles

Textweft의 **제품·설계·개발 판단 원칙**이다. 요구 범위는 [GOAL](GOAL.md), 확정된 기술 선택은 [Architecture Decision](architecture.md), 권한·승인·검증 절차는 [AGENTS](../AGENTS.md)와 [Development Guide](development/README.md)가 소유한다. 이 문서는 그 계약을 대체하지 않는다.

## Product

- **Vibe-coder-first:** 게임 제작자가 엔진 내부를 몰라도 자연어 요구 → 게임 정의 → 실행 → 오류 수정의 흐름을 반복할 수 있어야 한다.
- **Data-first:** 읽고 검증할 수 있는 콘텐츠를 우선하며, 필요한 게임별 동작만 명시적으로 확장한다.
- **Genre-neutral:** 장면·상태·규칙을 재사용 가능하게 설계하고 특정 장르의 관습을 코어에 고정하지 않는다.
- **Headless core:** 게임 규칙·상태와 표시·입력·배포 책임을 분리한다.
- **Reliable progress:** 상태 전이·난수의 재현성, 실패 시 원자성, 저장·복원의 정합성을 실제 검증으로 확인한다.

## Engineering

- **KISS:** 현재 요구를 충족하는 가장 단순한 구조를 선택한다. 짧은 코드보다 이해·검증·운영하기 쉬운 설계를 우선한다.
- **YAGNI:** 검증되지 않은 미래 기능을 위한 API·플러그인·추상화·도구를 미리 만들지 않는다.
- **DRY:** 함께 변경해야 하는 안정된 지식·계약만 한곳에서 관리한다. 우연히 비슷한 코드를 성급하게 공통화하지 않는다.
- **SRP:** 모듈과 문서는 책임·변경 이유에 따라 분리한다. 파일 수를 늘리기 위한 분리는 피한다.
- **Explicit contracts:** 입력·출력·상태 소유권·실패 처리를 드러내고, 잘못된 게임 정의에 수정 가능한 오류를 제공한다.
- **Evidence over assumptions:** Rust 컴파일러와 정적 검사는 활용하되 정확성을 자동 보장한다고 간주하지 않는다. 타입·테스트·실행·CI의 실제 근거를 구분한다.

## Decision Check

설계나 구현을 추가할 때 다음을 점검한다.

1. **현재 범위**인 텍스트·정적 이미지 게임에 필요한가? 아니라면 후속 검토로 남긴다.
2. 게임 제작자의 사용성과 엔진의 정합성을 개선하는가?
3. 같은 요구를 더 적은 개념·의존성·운영 비용으로 충족할 수 있는가?
4. 공개 계약과 오류·실패 경로를 독립적으로 검증할 수 있는가?

원칙이 충돌하면 **정합성과 게임 제작 경험을 지키는 가장 작은 검증 가능한 설계**를 우선한다.
