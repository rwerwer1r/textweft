# Test-driven Development

Textweft의 TDD는 테스트 개수나 기계적인 Red/Green ceremony가 아니라 **명세를 구현보다 먼저 실행 가능한 검증으로 바꾸는 방식**입니다. 테스트 선택과 oracle 품질은 `mols-test-design`, 순서는 `workflow-delivery`가 소유합니다.

## Work Order

1. **Spec:** 기대 동작·오류·경계·비목표를 정합니다.
2. **Test Design:** 최소 정상·경계·예외·회귀 사례와 독립 oracle을 설계합니다.
3. **Test Implementation:** 제품 코드 수정 전에 테스트를 작성하거나 기존 테스트가 동일 계약을 충분히 보호함을 확인합니다.
4. **Red:** 가능한 경우 변경 전 테스트가 의도한 결함 때문에 실패하는지 관찰합니다. fixture·환경·테스트 자체 오류와 구별합니다.
5. **Green:** Spec을 만족하는 최소 구현을 하고 새·기존 테스트를 통과시킵니다.
6. **Refactor:** 동작을 보존하며 구조를 개선하고 관련 테스트를 다시 실행합니다.
7. **Review:** Spec ↔ 테스트 설계 ↔ 테스트 코드 ↔ 제품 구현의 정합성을 확인합니다.

## Oracle and Test Boundaries

- 기대값은 Spec, 외부 계약, 확정된 예시, 신뢰 가능한 기준 동작 또는 독립 성질에서 도출합니다. 현재 구현을 유일한 oracle로 삼지 않습니다.
- 테스트는 현실적인 잘못된 구현을 구별해야 합니다. 실행만 하는 테스트나 내부 자료구조에 과적합된 assertion을 피합니다.
- 순수 로직에는 좁은 단위 테스트를, API·상태·권한·통합 경계가 중요하면 contract/integration/e2e 검증을 선택합니다. 가장 싼 충분한 경계를 사용합니다.
- fixture 격리, mocking 충실도, 병렬성·시간 의존, flakiness, 진단 가능성과 유지 비용을 고려합니다.

## Exceptions

이미 통과하는 유효한 회귀 테스트를 억지로 실패시키지 않습니다. 테스트 실행이 불가능하거나 oracle이 불명확하면 이를 명시하고 필요한 테스트 가능성 개선 또는 사람 결정을 요청합니다. 문서 오타·포맷처럼 실행 동작이 바뀌지 않는 작업에는 무의미한 테스트를 만들지 않습니다.

테스트 통과는 Spec 전체·사용자 경험·런타임 로딩·배포가 성공했다는 뜻이 아닙니다. 실제 실행과 미실행을 구분합니다.
