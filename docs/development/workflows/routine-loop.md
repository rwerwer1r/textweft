# Routine Working Loop

일반 작업은 **점검 → 범위·필요 시 계획 → 구현 → 검증 → 자체 리뷰 → PR/인계**로 진행하며, 새 근거가 생기면 앞 단계로 되돌아갈 수 있습니다. 단계는 반드시 수행해야 하는 형식적 의식이 아니라 작업 상태입니다. Textweft는 **바이브코딩**으로 개발하며, 자연어 요구와 역할 분담은 [바이브코딩 워크플로](vibe-coding.md)에서 설명합니다. 작업 단계와 권한 경계는 그대로 유지합니다.

## 1. Inspect and scope

정확한 저장소·연결 계정·브랜치/ref·권한, 루트 및 해당 경로의 하위 `AGENTS.md`, [에이전트 자산 라우터](../../../.agents/route/ROUTE.md)를 확인합니다. 관련 코드·제품 문서만 읽고 기존 작업 브랜치나 PR이 있는지 점검하여 중복 생성을 피합니다.

의도한 최소 변경, 수용 조건, 알려진 위험과 요청 단계를 정리합니다. 자연어 요구를 사용자 경험과 관찰 가능한 결과로 해석하되 일반적인 코드 구조 선택을 사용자에게 매번 요구하지 않습니다. 아키텍처·보안·호환성의 중요한 변경이나 파괴적 외부 효과가 예상되면 먼저 사람의 판단을 구합니다.

## 2. Change and preserve

리뷰할 변경에는 전용 브랜치를 사용합니다. 새로운 종속성이나 프로젝트 전체 시스템을 추가하기보다 작고 국소적인 변경을 선호합니다. Textweft 작업을 이유로 다른 저장소를 수정하지 않습니다.

복원 가치가 있는 다단계 작업은 처음으로 유용한 중간 상태가 생긴 시점에, 다음 길거나 위험한 작업 **이전**에 브랜치의 단일 [인박스 작업 상태](../../../inbox/README.md)를 PR 연계 또는 날짜 기반 경로에 저장하고 원격에서 재확인합니다. 모든 도구 호출마다 갱신하지 말고 중요한 결정·장애·검증 결과가 바뀔 때만 갱신합니다.

## 3. Validate

의존성을 설치한 후 Node.js 22.16 이상에서 다음 명령을 사용합니다.

```sh
npm test
npm run typecheck
npm run harness:check
```

diff에 해당하는 검사만 선택합니다. 게임 런타임 계약을 변경했다면 특히 잘못된 선택지, 전이의 원자성, 시드 난수 결정성, 관련 복원 호환성에 대한 집중 테스트가 필요합니다. 바이브코더의 저작 경험을 바꿨다면 공개 예제로 생성·실행·오류 수정 경로도 확인합니다. 문서만 변경했을 때는 보통 링크·카탈로그 검사와 집중 리뷰를 수행하며, 실제 런타임 테스트를 하지 않았다면 통과했다고 주장하지 않습니다.

**로컬에서 실행함 / CI에서 보고됨 / 수동 확인함 / 실행 불가 / 미실행**을 구분합니다. 서로 같은 수준의 근거로 취급하지 않습니다.

## 4. Review and publish

실제 변경된 파일을 대상으로 범위·기밀·링크 경로·문서 소유권·정책 충돌·의도하지 않은 코드 변경·테스트 공백을 검토합니다. 문제를 수정하고 영향받는 검사를 다시 수행합니다.

구현·문서 변경은 요약, 검증 근거, 한계, 남은 의사결정을 담아 PR을 생성하거나 갱신합니다. 명시적 요청과 필요한 검사·승인이 없으면 **병합하지 않습니다**. 막힌 작업은 성공했다고 주장하지 말고 구체적인 다음 행동을 인계합니다.

## Completion

의도한 변경이 정확한 브랜치에 존재하고, 관련 검증 상태가 사실대로 보고되며, 알려진 문제를 해결하거나 공개하고, 무단 부수효과가 없다면 PR은 사람의 리뷰를 받을 준비가 된 것입니다. 최종 병합·릴리스는 별도의 승인 게이트입니다.
