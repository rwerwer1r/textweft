# Routine Working Loop

프로젝트의 복잡한 RPI 실행·재귀·재계획은 [mols-loops 의존성](../tooling/agent-assets.md)이 담당합니다. 이 문서는 공통 확인·검증·인계만 소유하고, 동작 변경 Work에는 [workflow-delivery](../../../.rulesync/skills/workflow-delivery/SKILL.md)의 테스트 우선 절차를 적용합니다. 요청 단계의 권한은 [Workflow Selection](choosing.md), AI 협업은 [Vibe Coding](vibe-coding.md)을 따릅니다.

## Common Checks and Handoff

1. **시작:** 현재 저장소·계정·ref·권한·[AGENTS.md](../../../AGENTS.md)와 필요한 [Rule·Skill](../../../.agents/route/ROUTE.md), 기존 PR·코드·테스트를 확인합니다.
2. **범위:** 수용 조건과 검증 방법을 정하고 작은 작업 단위를 유지합니다. 중요한 제품·보안 결정은 사람에게 맡깁니다.
3. **검증:** [mise 작업](../README.md#checks) 중 관련 검사를 실행합니다. 전체는 `mise run check`, 작은 문서 변경은 `mise run lint:md` 등으로 범위를 줄입니다. [Lefthook](../../../lefthook.yml)은 관련 스테이징 파일만 검사하므로 전체 검증을 대체하지 않습니다. **실제 실행/CI/정적 확인/미실행**을 구분합니다.
4. **커밋 체크포인트:** 의미 있는 변경·인계 단위는 [Commit Checkpoints](#commit-checkpoints)를 따라 Conventional Commits 형식으로 커밋하고, 재개할 때 필요한 단서만 남깁니다.
5. **리뷰·인계:** 계약 위반·회귀·보안·명세와 테스트의 불일치를 자체 리뷰하고, 결과·검증 증거·위험·필요한 결정을 PR에 남깁니다. **병합은 별도 승인**입니다.

복잡한 다단계 작업만 첫 의미 있는 상태 이후 다음 긴/위험한 단계 **전에** 여러 커밋에 걸친 목표·의존성·진행 상황 등 커밋으로 표현하기 어려운 맥락을 [Inbox](../../../.inbox/README.md)에 최소 기록해 원격 보존·재조회합니다. 도구 호출마다 기록하지 않습니다.

## Commit Checkpoints

커밋은 **변경 단위의 스냅샷과 세션 재개 단서**입니다. 미커밋 변경이나 장기 작업 전체 상태까지 복원하지는 못합니다.

- **단위:** 줄 수·파일 수·세션 길이가 아니라 **함께 이해·검토·검증·되돌릴 수 있는 변경 목적**으로 묶습니다. 한 목적을 완성하는 코드·테스트·설정·문서는 함께 포함할 수 있고, 독립된 목적은 분리합니다. 하나의 PR에 여러 커밋이 있어도 됩니다.
- **시점:** 의미 있는 진척이나 인계 필요가 있을 때 커밋합니다. 도구 호출·세션 종료마다 커밋을 강제하지 않습니다. 미완료 작업을 작업 브랜치에 체크포인트로 남긴다면 **미완료·미검증 범위**를 밝혀 통합 가능한 완료 결과로 오인하지 않도록 합니다.
- **메시지:** 제목은 Conventional Commits(`type(scope): 요약`, scope 선택)로 **무슨 변경인지** 식별합니다. 본문은 필요할 때만 **왜 바꿨는지**, diff·PR·명세에 없는 중요한 결정, 실제 검증과 한계, 다음 확인 조건을 자연스럽게 보완합니다. 고정된 복구 필드나 중복 요약은 요구하지 않으며, 미실행 검사를 통과로 적거나 커밋 SHA를 미리 기입하지 않습니다.
- **게시·재개:** 다른 세션에서 읽으려면 조회 가능한 원격 ref에 커밋을 반영하고 재조회합니다. 재개할 때는 저장소·계정·브랜치/PR·현재 작업 트리부터 확인하고, 관련 커밋(반드시 HEAD일 필요는 없음)의 메시지·스냅샷을 **이후 변경·현행 계약·검증 근거**와 대조해 필요한 검증을 다시 합니다. 다른 작업자의 미커밋 변경을 덮어쓰지 않습니다.
- **이력·보안:** 커밋은 과거 기록이지 현재의 승인·검증 근거가 아닙니다. 게시된 커밋의 분할·재배열·rebase·amend는 협업자의 의존성과 권한을 확인한 뒤에만 수행합니다. squash 병합이나 브랜치 삭제로 체크포인트를 찾기 어려워질 수 있으므로 오래 유지할 결정은 정본·PR에 남기고, 메시지에 비밀·개인정보·민감한 대화를 적지 않습니다.

예시(실제 검증 결과가 아닌 메시지 형식):

```text
docs(harness): 체크포인트 재개 기준 명확화

세션 재개 시 커밋의 검증 상태를 현재 상태와 혼동하지 않도록
원격 ref와 이후 변경을 대조하는 절차를 명확히 함.

문서 내용은 정적 확인했지만 Markdown lint는 미실행.
최종 PR 리뷰 전에 링크 검사를 확인할 것.
```
